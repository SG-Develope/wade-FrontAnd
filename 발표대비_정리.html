WADE 최종발표 대비 정리

낙동강 실시간 수위 모니터링 · 프론트(wade) + 백엔드(wade-api) 1인 풀스택 프로젝트

기술스택·버전·이유 / 로직 흐름 / 코드 동작방식 / 예상질문을 한 문서로 정리

0. 한 문장 요약 (엘리베이터 피치)

낙동강홍수통제소가 공개하는 날것의 수위 숫자(예: "양포교 3.7m")를, 강변 캠핑·낚시·자전거·산책 이용자가 이해할 수 있는 "지금 가도 되는지"라는 장소 기반 안전 정보로 번역해주는 실시간 서비스입니다. 기존 조기경보는 기관이 판단해 문자를 보내야 시민이 알 수 있었지만, WADE는 시민이 능동적으로 현재 상황을 확인하고 스스로 판단하게 합니다.

1. 기술 스택 — 무엇을, 어떤 버전으로, 왜

1-1. 프론트엔드 (wade)

기술버전왜 이걸 썼나 (발표용 답변)
React19컴포넌트 기반 UI. 상태에 따라 자주 바뀌는 대시보드/차트/지도에 적합.
TypeScript6.x복잡한 외부 API 응답을 타입으로 고정 → 런타임 오류를 컴파일 단계에서 차단. strict 사용.
Vite8빠른 HMR·빌드. CRA보다 경량. @ → src 경로 alias.
Tailwind CSSv4유틸리티 클래스로 빠른 반응형 UI. v4는 @tailwindcss/vite 플러그인으로 config 불필요.
TanStack Queryv5서버 상태 핵심. 캐싱 + 자동 폴링 + 로딩/에러 선언적 처리. 수위 10분 자동 갱신.
Zustandv5클라이언트 상태(선택 관측소·모달). Redux보다 가벼운 스토어.
React Routerv7SPA 라우팅. 4개 페이지(대시보드/날씨/추이/여가).
Rechartsv324시간 수위 변화 라인 차트.
hls.js1.6CCTV 실시간 영상(HLS .m3u8)을 브라우저에서 재생.
axios1.xHTTP 클라이언트. 인터셉터로 요청/응답 로깅·에러 공통화.
핵심 개념 — "서버 상태 vs 클라이언트 상태 분리"
만점 답변: "API에서 온 데이터(수위·날씨)는 TanStack Query가, 순수 UI 상태(모달·선택값)는 Zustand가 관리하도록 역할을 나눴다."

1-2. 백엔드 (wade-api)

기술버전왜
Spring Boot4.0.7REST API 서버. 외부 공공 API 프록시·가공 + DB 관리.
Java21 (toolchain)LTS. switch 표현식·record 등 최신 문법.
Gradle—빌드. io.spring.dependency-management로 버전 관리.
MyBatis4.0.1SQL을 XML 매퍼에 직접 작성 → 쿼리 완전 제어. 단순 조회 위주라 JPA 대신 선택.
Caffeine Cache—인메모리 캐시. AI 브리핑을 10분 캐싱해 외부 AI 호출·비용 절감.
PostgreSQL (Neon)—서버리스 Postgres. 관측소·CCTV·장소·격자좌표 메타데이터 저장.
Lombok—@Data, @RequiredArgsConstructor로 보일러플레이트 제거.
Jackson—외부 API JSON 파싱(ObjectMapper, JsonNode).
DB에 저장 vs 실시간 조회 (자주 나올 질문)
· DB(정적): 관측소 기준수위, CCTV 위치, 여가 장소, 기상청 격자좌표(nx/ny)
· 실시간(외부 API): 현재 수위·이력, 날씨, 레이더/위성/태풍, AI 브리핑, CCTV 스트림 URL
→ "자주 안 바뀌는 건 DB, 계속 바뀌는 건 API"로 분리.

1-3. 외부 API (데이터 출처)

  • 낙동강홍수통제소 (HRFCO) — 수위 현재값/이력 (10분·1시간 간격)
  • 기상청 (공공데이터포털) — 초단기실황·초단기예보·단기예보·특보·레이더·위성·태풍
  • 국가교통정보센터 ITS — 도로 CCTV 실시간 HLS 스트림
  • Google Gemini (gemini-2.0-flash) — AI 안전 브리핑 생성 ⚠️(README엔 "Claude"로 표기 — 6장 참고)

1-4. 배포

프론트: netlify.toml 존재 → Netlify(SPA 리다이렉트). 백엔드: Procfile → Railway 계열 PaaS. (README 표기는 Vercel/Railway로 최신화 안 됨)

2. 시스템 아키텍처 & 데이터 흐름

[사용자 브라우저]
    │  ① 메타데이터 (/api/stations, /places, /cctv, /weather/*, /ai/*)
    ▼
[React SPA] ─────────► [Spring Boot (wade-api)] ──► [PostgreSQL / Neon]
    │                        │
    │                        ├──► 기상청 API   (날씨·레이더·위성·태풍)
    │                        ├──► Gemini API   (AI 브리핑, 10분 캐시)
    │                        └──► ITS API      (CCTV 최신 스트림 URL)
    │
    │  ② 실시간 수위는 프론트가 HRFCO를 "직접" 호출
    └────────────────────────────────► [HRFCO api.hrfco.go.kr]
⚠️ 꼭 알아야 할 포인트: 수위 데이터는 두 경로가 공존
백엔드에도 WaterLevelService가 구현돼 있지만, 실제 프론트(waterLevel.ts)는 백엔드를 거치지 않고 HRFCO를 직접 호출합니다. 관측소 메타데이터(기준수위·obsCode)만 백엔드 /api/stations에서 받고, 현재 수위·이력 숫자는 브라우저에서 직접 조회.

왜? 백엔드 서버 IP가 HRFCO에 차단될 수 있어(주석에 "IP 차단 가능"), 클라이언트 IP로 분산. 백엔드엔 동일 로직을 fallback으로 보유.

3. 백엔드 레이어별 동작 방식

표준 Spring 3계층: Controller(HTTP) → Service(로직·외부 API) → Mapper(MyBatis SQL) → DB

3-1. 설정 (config)

  • CacheConfig — Caffeine. 캐시 aiGuide, cctvUrls. 10분 만료, 최대 50개.
  • CorsConfig — /api/** CORS 허용(allowedOriginPatterns("*")).
  • RestTemplateConfig — ⭐ ① @PostConstruct에서 SSL 인증서 검증 전역 비활성화(공공 API의 PKIX path building failed 회피) ② RestTemplate Bean(connect 10s / read 15s).
보안 질문 대비: SSL 검증을 끄는 건 실무에선 위험 → "공공 API 인증서 이슈 회피용 임시 조치, 운영에선 truststore에 인증서 등록으로 전환해야 한다"고 답변.

3-2. 수위 서비스 (WaterLevelService)

현재: DB 관측소 순회 → obsCode로 HRFCO 10M 호출 → content[0].wl 파싱 → 상태 계산. 이력: hours≤6이면 10분 간격, 초과면 1시간 간격. Asia/Seoul 기준, 10분 단위 내림. 응답이 최신→과거 순이라 Collections.reverse()로 시간순 정렬. calcStatus: 심각→경보→관심 순 비교, 데이터 없으면 -1→unknown.

3-3. 날씨 서비스 (WeatherService) — 가장 복잡

기상청 API 7종. 핵심은 base_time(발표시각) 계산:

  • 초단기실황: 매시 정시 발표, 10분 후 제공 → 분<10이면 이전 시간.
  • 초단기예보: 매시 30분 발표, 45분 후 조회 → 분<45면 이전 시간의 HH30.
  • 단기예보: 하루 8회(02·05·08·11·14·17·20·23시) → 현재 이하 가장 최근 발표시각.
  • 격자좌표: 위경도 대신 기상청 전용 격자(nx/ny). DB weather_grid 매핑(구미 86/96, 칠곡 85/93).
  • 파싱: 같은 시각의 여러 category(TMP·SKY·POP·PTY)를 날짜+시각 key로 묶어 한 객체로 조립.
  • 에러: 429(한도 초과)는 별도 처리 + GlobalExceptionHandler 전역 처리. 코드→한글 변환 헬퍼(하늘·강수형태·풍향).

3-4. AI 브리핑 서비스 (AiGuideService) — 발표 하이라이트

  1. 프론트가 현재 수위 {yangpo, hoguk}를 POST.
  2. 캐시 키: 수위를 0.1m 단위 반올림 → 수위 비슷하면 같은 캐시. 10분간 동일 요청은 AI 재호출 안 함(@Cacheable).
  3. 프롬프트: 각 관측소 수위·단계·기준수위·관심수위 대비 차이 + 체감 높이 라벨("버스 지붕 높이")을 넣어 Gemini에 전달. JSON만 응답 지시.
  4. 파싱: 코드펜스 제거 후 {...}만 추출 → message + activities(산책/낚시/자전거/캠핑).
  5. Fallback: AI 키 없거나 실패 시 규칙 기반 메시지(4단계 템플릿) → AI가 죽어도 서비스는 동작.
heightLabel이 수위 숫자를 "성인 허리 높이", "버스 지붕 높이"로 번역 → "숫자를 안전 정보로 번역"이라는 서비스 정체성을 코드로 구현한 부분.

3-5. CCTV 컨트롤러

DB CCTV 목록 조회 후 ITS API로 최신 스트림 URL 실시간 갱신(enrichWithFreshUrl). ITS URL은 만료되므로 매번 재조회. 위경도로 bounding box 만들어 질의 → cctvname 일치 항목의 cctvurl로 교체. 실패 시 DB URL로 fallback.

3-6. 매퍼 (MyBatis)

Station/Cctv/Place/StationMeta/WeatherGrid + 각 .xml. schema.sql로 테이블 생성, data.sql로 초기 데이터(ON CONFLICT DO UPDATE로 재실행 안전).

4. 프론트엔드 동작 방식

4-1. 진입 & 구조

main.tsx: QueryClientProvider(retry 1, staleTime 10분) + RouterProvider. App.tsx: 상단 네비(데스크톱)/하단 탭바(모바일) 반응형, <Outlet/>에 페이지. 라우트 4개, 루트는 dashboard 리다이렉트.

4-2. 데이터 페칭 패턴 (핵심)

api/*.ts(fetch) → queries/*.ts(useQuery 훅) → 컴포넌트. queryKeys로 키 계층 관리. 폴링: 수위/AI/현재날씨 10분, 단기예보/특보 1시간, 레이더 5분, 위성 10분, 태풍 30분. placeholderData:(prev)=>prev로 리페치 중 깜빡임 방지.

4-3. 대시보드 흐름

① 수위 조회 → ② 수위 맵을 AI 브리핑에 전달 → ③ 위험 관측소 있으면 DangerBanner 자동 노출 → ④ KakaoMap에 상태별 색상 마커, CCTV 클릭 시 모달 → ⑤ RightPanel에 수위·날씨·AI 카드.

4-4. CCTV 영상 재생 (HlsPlayer)

hls.js로 .m3u8를 <video>에 연결. 지원 안 되면(사파리) 네이티브 재생. ITS의 http://를 https://로 바꿔 mixed-content 회피. 치명적 에러 시 콜백으로 대체 UI.

4-5. 상태 관리 (Zustand)

선택 관측소·활성 탭·선택 마커 + 모달 열고 닫기. 순수 UI 상태만 담당.

6. ⚠️ 예상 함정 질문 (Gotcha)

"코드 실제로 봤냐"를 확인하는 날카로운 질문들. 정직하게 인정 + 개선방향 제시가 정답.

  1. "AI가 Claude라면서 코드는 Gemini네요?"맞습니다. 문서엔 Claude(Anthropic)로 적혀있지만 실제 구현은 Google Gemini(gemini-2.0-flash). 개발 중 API 접근성 문제로 교체, 문서 갱신 누락.
  2. "배포는 Vercel/Railway라면서 netlify.toml이 있네요?"프론트는 실제로 Netlify로 배포(SPA 리다이렉트 포함). README 표기 미갱신.
  3. "수위는 백엔드가 주는 거 아닌가요? 왜 프론트가 HRFCO를 직접 부르죠?"2장 참고. HRFCO 서버 IP 차단 회피 + 메타/실시간 분리. 백엔드에도 동일 로직 fallback 보유.
  4. "SSL 인증서 검증을 전역으로 끄셨는데 보안 문제 아닌가요?"공공 API 인증서(PKIX) 오류 회피용 임시 조치. 운영에선 truststore 등록으로 전환 필요(인지함).
  5. "API 키가 코드/설정에 하드코딩돼 있네요?"application-local.properties와 waterLevel.ts fallback에 노출. 발표 후 즉시 환경변수/시크릿 분리 + 노출 키 폐기·재발급 권장.
  6. "상태 판단 기준이 서비스마다 다르지 않나요?"실제로 WaterLevelService(주의=관심수위), AiGuideService(주의=주의보수위), 프론트 constants(옛 하드코딩값)가 일부 불일치. DB값이 최종 소스, 프론트 constants는 초기 목업 잔재. 통일 필요.
  7. "캐시 이름 cctvUrls는 실제로 쓰나요?"CacheConfig에 선언은 있지만 CctvController가 @Cacheable을 안 붙여 현재 미사용. aiGuide만 실제 캐싱.
  8. "@EnableScheduling을 켰는데 스케줄 작업이 있나요?"어노테이션만 있고 @Scheduled 메서드는 없음. 확장 대비 흔적.
  9. "에러 나면 사용자는 뭘 보나요?"각 쿼리에 로딩 스켈레톤/에러+재시도 UI. AI는 실패 시 규칙기반으로 대체돼 빈 화면이 안 나옴.

7. 30초 발표 오프닝 스크립트

"WADE는 낙동강홍수통제소의 실시간 수위 데이터를 강변 여가 이용자용 안전 정보로 번역하는 서비스입니다. 프론트는 React 19·TypeScript·TanStack Query로 서버 상태를 10분마다 자동 갱신하고, 백엔드는 Spring Boot 4·Java 21로 기상청·ITS·AI API를 통합합니다. 핵심은 '3.7m'라는 숫자를 '버스 지붕 높이 — 지금은 위험'처럼 누구나 판단할 수 있는 언어로 바꾸는 것이고, AI 브리핑이 실패해도 규칙기반으로 대체되도록 설계했습니다."

8. 빠른 자문자답 체크리스트

  • Q. 서버/클라이언트 상태를 왜 나눴나? → TanStack Query(서버) / Zustand(UI).
  • Q. 왜 JPA 아니고 MyBatis? → 단순 조회 위주, SQL 직접 제어가 명확.
  • Q. 왜 Caffeine 캐시? → 외부 AI 호출 비용/지연 절감, 10분 캐시.
  • Q. 기상청 격자좌표(nx/ny)가 뭔가? → 위경도 대신 기상청 전용 격자. DB에 관측소별 매핑.
  • Q. base_time 계산이 왜 필요? → 발표 전 시각을 요청하면 빈 응답 → 가장 최근 발표시각 계산 필수.
  • Q. HLS가 뭔가? → HTTP 기반 적응형 스트리밍(.m3u8). CCTV 실시간 영상, hls.js로 구현.
  • Q. 이 서비스의 차별점? → 수동 통보형 조기경보와 달리 시민이 능동 확인 + 숫자를 체감 언어로 번역.
